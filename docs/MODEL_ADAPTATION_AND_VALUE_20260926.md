# 按模型编译与能力边界

HEX 把用户目标、设计决定和目标模型能力结合后编写提示词。宿主负责理解与创作，程序负责核对来源、版本、动作覆盖和实际调用参数；通过这些核对不等于画面已经满足要求。

## 最小工作顺序

1. 保存用户原话与必要素材，形成当前 Need。
2. 明确必须保留的事实、本次修改目标和可自由发挥的部分，形成一个有效 Plan。
3. 根据实际可用工具和模型档案准备编译输入，写出完整正文。
4. 完成 preflight；要求成图时继续冻结输入、dispatch、真实执行和结果检查。只要提示词时完成对应导出流程。

例如，宿主使用当前 Image 工具时：

```text
python -m hex_agent prepare-compilation --run outputs/task --plan outputs/task/plan.json --target image --tool image_gen.imagegen
```

这一步生成 `compilation-input.json`，本身不调用模型。目标模型或工具不同，应使用真实对应值，不能只替换标签。完整操作见 [CODEX_START.md](../CODEX_START.md)。

## 编译时保留什么

- **任务事实：**主体身份、用途、数量、文字、修改范围、素材职责和用户锁定的构图。
- **设计决定：**本题采用的动作、空间、光线和材质关系，以及这些决定的依据。
- **实际控制：**当前工具真正暴露的图片输入、尺寸、比例、质量等参数；未暴露的能力保持未控制。

正文长度和组织由本题与目标模型决定，不预设固定文体，也不为制造模型差异删掉关键要求。只保留有实际作用的约束；可自由发挥的部分不要提前锁死。

每份编译的 `adaptation` 说明采用了哪些当前规则，并引用正文片段。程序核对任务、设计、档案版本、规则与实际片段的绑定；这些检查不能证明语义等价或生成效果。

计划、父图、修改要求或工具能力变化后，应重新准备编译输入并预检，不能修改已冻结的请求后直接执行。返修正文须同时保留正确部分和明确修改目标，沿真实父图、原授权与累计预算继续。

## 查看当前能力

```text
python -m hex_agent executors
```

执行器目录提供已接入路线及声明的控制范围，不会自动安装模型、探测服务或生成图片。实际使用前仍需确认对应工具、账号、本地服务与模型可用。

模型资料位于 [knowledge/models](../knowledge/models)，保留资料来源、核对日期和适用范围。档案中的模型名称、官方 API 标识、服务商名称和宿主工具身份分别看待，不能凭某一平台文档推断另一工具的具体版本或实参。

结果页与 `design-explanation.md` 可展示原话、设计取舍和模型正文。没有真实调用回执的正文应称为已编译内容，不能称为已发送内容。

## 内测如何判断价值

先看实际结果是否实现用户核心目标、保留应保留的内容，再记录耗时、修改次数和主要失败。工程通过、工具成功、视觉效果与用户接受分别保存。

比较不同写法或 HEX 与手工提示词时，使用同一模型、相同素材与信息、相等请求预算，隐藏来源后让测试者比较，并允许“相当”或“都不接受”。小样本结果只说明该任务，不能据此宣称跨模型的稳定审美优势。双模型比较也应共用同一需求与设计，分别编译和冻结，沿同一实际许可与累计预算执行。
