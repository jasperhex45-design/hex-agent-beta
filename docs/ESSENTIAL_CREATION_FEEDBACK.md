# 必要关系、允许变化与真实看图反馈

HEX 的交付目标是原图实现用户意图。提示词存在、调用成功和局部检查通过，只能说明对应步骤有证据；它们不能代替整图判断或用户接受。

## 创作只控制有作用的内容

本轮沿用已有 Need、Plan、模型编译和冻结检查，不增加阶段或分类 schema。

| 内容 | 放在哪里 | 如何处理 |
| --- | --- | --- |
| 用户明确要求的身份、数量、文字与范围 | Need 的原话来源与必要约束 | 不得在设计或编译时擅自改掉。 |
| 使当前画面成立的必要关系 | `choices.action`、`cooperation` | 写出可见关系及作用，不能只有风格名或评价词。 |
| 可以有不同实现的细节 | 同一 `action` 的允许变化边界 | 编译保留自由度；冻结 checks 使用相同边界。 |
| 可以让位的视觉收益 | `tradeoff` | 说明真正的取舍，不能以事实准确或权限作为牺牲项。 |
| 无助于目标的细节 | 在最终选择前省去 | 不先塞满 Plan，再由编译器偷偷删去。 |

Image 摄影指导按实际主体和可见动作选择必要关系。只有人物动作或接触承担表达时，才说明可见手部职责与支撑；不为补齐未入镜的身体改变取景。所有已经选定的 choice 仍须进入实际正文，可合并重复描述，但不能漏掉必要关系，也不能把允许变化的实现升级为必需。

这不等于提示词越短越好。判断依据是内容是否帮助实现本题，及其在原图中的实际效果。

## 看出失败与定位原因分开

用户可以直接用图片判断效果。HEX 负责维护同一请求的需求、方案、实际提示词、输入素材、原图与评审绑定，供后续回查。

- 首次视觉评审只依据原始目标、候选与必要参考判断可见结果。
- 看见差距可以记录 `not_met`；不知道原因仍保留 `unknown`。
- 默认完整流程的案例记录不会把首评的 `design` 等判断升级为已确认根因；它只保留为 `reported_hypothesis`。
- 第二阶段诊断才结合原方案和实际调用，按每个问题查最早能证明的偏差；文本一致也不自动证明语义等价或因果。

例如，成图有回头姿势，实际提示词也主动要求回头，这首先说明该设计已被传递；单凭图片不能说模型没听指令。方案可能被忠实执行，却仍没有达到用户想要的效果。

## 失败也有带图反馈

`workflow record-review` 保存有效评审后，直接生成 `workflow/feedback/` 下的 HTML 反馈页，不依赖 `workflow complete` 或成功导出。页面嵌入当前候选的原始图片字节，并展示目标、整体观察、具体差距、待验证建议和实际提示词。它是可查看的反馈产物，不自动记录用户选择。

若检查已运行但质量未满足，`workflow status` 保留 `candidate_receipts` 和 `feedback_cards`。尚未核验或已失效的文件检查会明确显示缺口；它们不应抹掉有效的视觉评审。

`harness case` 与 `diagnosis prepare` 读取并核验同一请求在 `workflow/reviews` 中的评审。生产路线在成功导出前尚未写入旧 trial 文件时，复用已有执行账本的只读投影，不伪造试图或评审。已经存在但摘要、图片或请求失配的记录必须报错，不能静默退回旧内容。

历史任务继续使用原生评审路径。显式研究配置中的原生失败，不会被后来的正向完整流程评审覆盖。

## 本轮验证能说明什么

针对性测试核验失败与不确定状态的反馈可达性、原图字节、实际调用绑定、旧任务兼容，以及读取诊断时不追加生成或修改原任务。测试图片与评审是合成数据，不能作为审美证据。

真实出图另行保留原始文件和执行记录。工程修改通过、图片生成成功、视觉目标达到、用户接受分别汇报。单张结果即使改善，也不足以证明长期稳定收益；如果整体仍然普通或不自然，应保留未满足状态。
